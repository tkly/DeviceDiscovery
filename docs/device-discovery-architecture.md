# 设备发现系统设计（PC 跨平台 + 嵌入式 C++）

## 1. 目标与约束

- **目标**：在同一局域网内，让 PC 端应用能自动发现嵌入式设备，并建立后续控制/数据通道。
- **PC 端要求**：跨平台（Windows/macOS/Linux）。
- **嵌入式端要求**：使用 C++ 实现。
- **网络现实**：设备和 PC 可能在不同子网、可能存在组播受限网络、可能有多网卡场景。

---

## 2. 先回答核心问题：谁做服务端？

你提出“PC 充当服务端还是嵌入式设备充当服务端”不确定，这是最关键的架构选择。

### 建议结论（推荐默认方案）

> **嵌入式设备做“发现服务端（Responder）”，PC 做“发现客户端（Controller）”。**

### 推荐理由

1. **符合业务直觉**：PC 通常是管理/运维端，主动扫描并管理设备最自然。
2. **支持一对多**：一个 PC 管理 N 台设备；设备被动应答即可。
3. **网络适配更稳**：PC 端网络环境复杂（多网卡/VPN），做主动方更容易补偿策略（多接口探测、并发重试）。
4. **设备资源友好**：设备不需要维护复杂连接池，仅需监听 + 返回自身信息。

### 何时考虑反过来（PC 做发现服务端）

- 设备主动上报是主流程（例如“设备开机自动找管控中心”）。
- 需要跨网段、跨 NAT 汇聚到固定中心（类似云注册）。
- PC（或服务器）有固定地址且长期在线。

> 如果你未来想同时支持两种部署，建议做成**双模式**：
> - 局域网即插即用：PC 主动发现设备（默认）。
> - 跨网段集中管理：设备主动注册到中心。

---

## 3. 推荐总体架构（双层发现）

采用“**本地快速发现 + 可选中心注册**”的两层架构：

1. **L1：局域网发现（必须）**
   - PC 发送 UDP 广播/组播 `DISCOVER`。
   - 设备回复 UDP 单播 `ANNOUNCE`（带设备元数据与能力）。

2. **L2：中心注册（可选）**
   - 设备向中心（可在 PC/服务器）周期心跳注册。
   - PC 可通过中心拿到在线设备列表（用于跨网段）。

对于你的当前诉求，先落地 L1 即可，L2 预留接口。

---

## 4. 通信协议建议

## 4.1 发现平面（Discovery Plane）

- **传输**：UDP
- **端口**：例如 `37020`
- **消息格式**：JSON（开发快）或 CBOR（更省流量）

### 消息 1：PC -> 设备 `DISCOVER`

```json
{
  "type": "DISCOVER",
  "request_id": "uuid",
  "client_id": "pc-xxxx",
  "protocol_version": 1,
  "need": ["control", "telemetry"],
  "nonce": "random"
}
```

### 消息 2：设备 -> PC `ANNOUNCE`

```json
{
  "type": "ANNOUNCE",
  "request_id": "uuid",
  "device_id": "dev-001",
  "model": "ABC-100",
  "fw_version": "1.3.2",
  "ip": "192.168.1.23",
  "control_port": 46000,
  "telemetry_port": 46001,
  "capabilities": ["relay", "sensor-temp"],
  "auth": {
    "scheme": "token|mtls|psk",
    "fingerprint": "..."
  },
  "ts": 1710000000
}
```

### 关键机制

- `request_id`：防止多次请求响应混淆。
- `protocol_version`：兼容未来升级。
- 设备应做**响应抖动**（例如 0~200ms 随机延迟）避免风暴。
- PC 端按网卡分别发送，并去重（按 `device_id`）。

## 4.2 控制平面（Control Plane）

- **推荐传输**：TCP + TLS（或 QUIC）
- **语义**：请求-响应（JSON-RPC/gRPC/自定义）
- **连接方向**：默认 PC 主动连设备 `control_port`

## 4.3 数据平面（Telemetry Plane，可选）

- 低频状态：可复用控制连接。
- 高频流数据：单独通道（UDP/QUIC/WebSocket 视场景选择）。

## 5. PC 跨平台实现建议

## 5.1 技术栈

- **语言候选**：
  - C++（Qt/Boost.Asio）：与设备端统一语言。
  - Rust：跨平台与并发可靠性好。
  - Go：网络开发效率高、跨平台构建简单。
- 若你团队主力是 C++，建议 PC 与设备都用 C++，共享协议模型与序列化库。

## 5.2 PC 客户端核心模块

1. `NetworkInterfaceEnumerator`：枚举可用网卡。
2. `DiscoveryEngine`：对每个网卡发送 `DISCOVER` 并收包。
3. `DeviceRegistry`：设备去重、状态机（ONLINE/OFFLINE/STALE）。
4. `SessionManager`：和设备建立 TLS 控制连接。
5. `AuthManager`：证书/令牌管理。
6. `UI/API Layer`：上层展示与操作接口。

## 5.3 多平台注意事项

- Windows 广播行为与 Linux/macOS 有差异，需单独适配 `SO_BROADCAST` 与网卡绑定。
- macOS 沙箱/权限会影响网络发现（若做 App Store 分发需提前评估）。
- VPN 虚拟网卡常导致重复发现或不可达地址，需要过滤策略。

## 6. 嵌入式 C++ 服务端建议

## 6.1 设备侧模块

1. `DiscoveryResponder`（UDP 监听与应答）。
2. `ControlServer`（TCP/TLS 指令处理）。
3. `DeviceIdentity`（设备唯一 ID、证书、密钥）。
4. `HealthReporter`（本地状态收集）。

## 6.2 嵌入式实现细节

- 优先事件驱动（epoll/select）而非“一连接一线程”。
- 对入站报文做长度与字段校验，避免异常包导致崩溃。
- 限流：同一源 IP 每秒响应次数限制（防扫描/风暴）。
- 持久化：设备 ID 与密钥放安全存储区。

---

## 7. 安全设计（必须）

1. **发现阶段最小化暴露**：仅返回必要元数据，不返回敏感信息。
2. **接入鉴权**：
   - 起步：预共享 token（PSK）
   - 进阶：mTLS 双向证书
3. **防重放**：`nonce + timestamp + 签名`。
4. **审计日志**：记录谁在何时发现/连接了设备。
5. **默认拒绝**：未认证连接只允许有限接口。

---

## 8. 可扩展性与兼容策略

- 协议头加入 `protocol_version` 和 `feature_flags`。
- 新字段“可选添加”，旧客户端忽略未知字段。
- 设备端支持“最小兼容窗口”（例如最近 2 个协议版本）。

---

## 9. MVP（最小可用版本）落地建议

### 9.1 里程碑

1. **M1：局域网发现跑通**
   - PC 发送 `DISCOVER`，设备回复 `ANNOUNCE`。
   - PC UI/CLI 列出在线设备。

2. **M2：控制连接跑通**
   - PC 与单设备建立 TCP/TLS。
   - 完成 `get_info`、`reboot`、`set_param` 三个示例命令。

3. **M3：安全加固**
   - 引入 token/mTLS。
   - 加入重放保护与基础审计。

4. **M4：稳定性**
   - 断网重连、设备上下线抖动抑制、压力测试。

### 9.2 验收指标（示例）

- 50 台设备同网段，发现时间 < 3 秒。
- 误发现率 < 0.1%。
- 设备离线检测时间 < 10 秒。
- 控制指令成功率 > 99.9%。

---

## 10. 最终建议（给你的决策）

如果你现在只做第一版：

- **角色选择**：设备做发现服务端，PC 做发现客户端（推荐）。
- **协议选择**：UDP 发现 + TCP/TLS 控制。
- **工程选择**：PC 端走跨平台网络框架；嵌入式端 C++ 事件驱动实现。
- **演进路线**：先局域网发现，再加中心注册能力。

这样做能最快得到可用系统，同时保留后续跨网段与云化演进空间。
